# Workflow Completion for Magic Layers

本文档用于定义 `Magic Layers` 下一阶段最重要的演化方向：

**从图层拆解功能（feature）进化为可学习的工作流入口（workflow entrypoint）**

这份文档承接前两份文档：

- `thought-completion-runtime.md`
- `result-feedback-loop-analysis.md`
- `chat-completion-signals.md`

如果说：

- `ChatPanel` 解决的是“怎么把想法写出来”
- `Result Feedback Loop` 解决的是“怎么知道什么结果真的有效”

那么 `Magic Layers` 要解决的是：

> 当一张图被拆成可编辑资产之后，系统如何判断用户接下来最可能要做什么，并把下一步工作流提前准备好。

---

## 一、为什么现在必须定义这条线

当前 `Magic Layers` 已经很强，它至少具备这些能力：

- 全图语义分析
- 自动识别并选中可编辑图层
- 批量提取图层
- clean plate / 回贴验证
- 后续图层编辑、局部重绘、独立资产编辑

也就是说，它已经不是一个单点抠图器，而是一个很像“图像资产化入口”的系统。

但当前它的产品体验仍然偏：

- 我帮你拆一张图
- 拆完你再自己决定下一步怎么做

这会导致一个明显问题：

> Runtime 已经开始记录用户行为和偏好，但 `Magic Layers` 这条链路本身还没有真正变成“系统越来越懂你下一步”的工作流。

换句话说，用户会感受到：

- 图层拆出来了
- 推荐也有一些
- 系统好像开始懂一点了

但不会强烈感受到：

- “这个系统知道我拆完之后通常会怎么继续”

这就是 `workflow completion` 要补上的部分。

---

## 二、`Magic Layers` 的真正定位

`Magic Layers` 不应该只被定义成：

- 图像拆层
- 高级抠图
- 语义图层编辑入口

更准确的定义应该是：

> 它是用户把一张静态图片转化为“可编辑、可复用、可继续生产”的视觉资产工程的入口协议。

这个定义很重要，因为它会直接改变你们对后续产品的判断。

如果把 `Magic Layers` 看作一个 feature，你们就会继续围绕：

- 分层更准
- 遮挡补全更强
- 边缘更干净

如果把它看作一个 workflow entrypoint，你们就会开始围绕：

- 拆完之后，用户第一件事最想做什么
- 哪些层最值得优先处理
- 哪些层最值得沉淀成资产
- 哪条后续操作路径最值得提前推荐

这两种思路决定的产品未来完全不同。

---

## 三、当前系统已经具备哪些“工作流雏形”

虽然 `Magic Layers` 还没有完全工作流化，但现在已经有一些很重要的基础。

### 1. 图像入口已经是语义化的，不是纯像素级的

当前系统在触发 `Magic Layers` 时，会先做：

- 全图语义分析
- 判断图层类型
- 识别背景与可编辑对象
- 生成可继续处理的图层结构

这说明入口已经不是“抠图”，而是“建立一个可编辑场景结构”。

### 2. 拆层之后已经能接多条后续链路

当前拆层之后，用户实际上已经可以走不同路径，例如：

- 独立资产编辑
- 融合编辑
- 回贴验证
- 保存资产
- 后续局部修改

这说明工作流分叉已经存在，只是系统还没有很好地帮助用户判断“哪条更适合当前任务”。

### 3. Runtime 已经开始记录拆层后的行为

虽然还没有完整的 `workflow completion`，但 `Dispatcher`、`CreativeMemoryLayer`、`SemanticRecommender` 已经在开始记录：

- 对哪些图层做了什么
- 常见意图是什么
- 哪些滑块和风格偏好常出现

所以从工程基础看，这条线不是从零开始。

---

## 四、现在最欠缺的不是“能力”，而是“下一步判断”

从产品角度看，当前 `Magic Layers` 最大的缺口不是拆得不够，而是：

> 拆完以后，系统还不够清楚地帮助用户判断“接下来最值得做什么”。

这会体现在几个具体问题上：

### 1. 哪些层应该优先处理

不是所有拆出来的层价值都一样。

例如：

- 海报里，产品主体、价格区、文案区，通常比装饰图形更重要
- 空间图里，主家具、主要软装，通常比背景纹理更重要

但当前系统还没有把这件事非常明确地产品化出来。

### 2. 哪些层适合哪种编辑路径

同样是拆出来的层，不同类型最适合的路径很不一样。

例如：

- `product_image` 更适合：独立编辑 -> 资产化 -> 变体
- `text / price_badge` 更适合：结构保持 -> 局部替换 -> 方案同步
- `background_plate` 更适合：延后处理 -> 回贴验证 -> 融合生成

当前系统还没有强到能自动把这些路径编排出来。

### 3. 哪些拆层结果值得沉淀成资产

系统现在可以存资产，但还不够懂：

- 哪类拆层资产是高复用的
- 哪类只是临时中间态
- 哪类适合成为模板的一部分

### 4. 哪些后续路径真正带来了好结果

如果系统不知道：

- 哪类拆层结果最终被导出
- 哪类拆层结果被入库
- 哪类工作流路径被重复采用

那它就很难真正“越来越懂”。

---

## 五、`Workflow Completion` 在 `Magic Layers` 里意味着什么

`Workflow Completion` 不是简单地在拆层后加一个推荐面板，而是意味着系统开始具备下面这些能力：

### 1. 拆完之后自动排序优先级

系统应该能根据：

- 当前任务类型
- 当前图层语义类型
- 用户历史偏好
- 后续结果统计

自动判断：

- 哪些层现在最值得先看
- 哪些层当前可以折叠或延后

### 2. 自动推荐下一步工作流

不是只推荐风格，而是推荐动作路径。

例如：

- `建议先提取主商品，再做 3 个促销变体`
- `建议先锁定价格区和产品图，再回贴整张海报`
- `建议先对主家具做独立资产编辑，再回贴到 clean plate`

### 3. 自动准备下一步操作入口

例如，系统知道你在类似任务里通常会：

- 先 isolated edit
- 再存入资产库
- 再做方案导出

那它就不该只“提醒”，而应该把这条链路更早浮出来。

### 4. 自动沉淀拆层结果的价值判断

例如：

- 这个层经常被保存成资产
- 这个层经常只是临时过渡
- 这个层经常参与最终导出

这些信息应该慢慢变成 Runtime 的长期知识。

---

## 六、如果这条路做成，用户会感受到什么

最终用户不应该只是感受到：

- “这个系统拆层挺准”

而应该感受到：

### 1. 它知道我拆完之后最想处理哪个对象

我不用先自己一个个看图层列表，系统已经把关键对象浮到了前面。

### 2. 它知道我通常怎么处理这类对象

例如：

- 商品图先提亮再独立编辑
- 空间主家具先提取再回贴
- 价格区先锁结构再换样式

### 3. 它知道哪些结果值得保存下来

系统不会把每个中间态都当成资产，而是越来越懂哪些拆层结果更可能成为长期素材。

### 4. 它让我更快进入下一步

这才是工作流最核心的体验：

- 不是让我多一个工具
- 而是让我少一次思考“接下来怎么办”

---

## 七、建议的最小工作流状态模型

为了让 `Magic Layers` 开始从 feature 走向 workflow，可以先建立一个很薄的工作流状态模型。

```ts
interface MagicLayerWorkflowState {
  itemId: string;
  sessionId?: string;
  startedAt: number;

  taskType?: string;
  sourceImageType?: string;

  extractedLayerIds: string[];
  selectedLayerIds: string[];

  nextSuggestedAction?: string;
  completedActions: string[];

  resultSignals?: {
    selected?: boolean;
    exported?: boolean;
    savedToAssetLibrary?: boolean;
    reused?: boolean;
  };
}
```

这个模型不是为了做完整流程引擎，而是为了先把：

- 起点
- 中间关键动作
- 结果信号

串成一条可学习的链。

---

## 八、第一阶段最值得记录的工作流事件

和 `result-feedback-loop-analysis.md` 一样，这里也不建议一开始记太多。

第一阶段建议先记下面这些。

### 1. `magic_layers_started`

定义：

- 用户触发了 `Magic Layers`

意义：

- 这是整条工作流的入口

### 2. `magic_layers_layers_selected`

定义：

- 系统自动选中了哪些层，用户手动保留/取消了哪些层

意义：

- 这是理解“哪些图层对用户真正重要”的第一步

### 3. `magic_layers_action_taken`

定义：

- 在拆层之后，用户对某个层执行了什么动作

例如：

- `isolated_edit`
- `fusion_sync`
- `recompose`
- `save_to_asset_library`

意义：

- 这是从“拆层”走向“工作流”的核心动作事件

### 4. `magic_layers_result_selected`

定义：

- 拆层链路产出的结果被选用

### 5. `magic_layers_result_exported`

定义：

- 拆层链路产出的结果被导出

### 6. `magic_layers_asset_saved`

定义：

- 拆层结果被保存为独立资产

### 7. `magic_layers_result_reused`

定义：

- 某个拆层资产再次被放入别的项目或方案

这些事件和 Result Layer 最终应该汇合，但第一阶段可以先在 `Magic Layers` 的视角看清楚。

---

## 九、第一阶段最值得先回答的 4 个问题

不要一开始就追求“系统完全懂用户”，先让系统能回答下面这 4 个问题就已经很有价值。

### 1. 用户在什么类型的图里最常点 `Magic Layers`

例如：

- 海报
- 餐饮广告
- 商品宣传图
- 空间图

### 2. 拆出来之后，用户最常先处理哪一类层

例如：

- 产品主体
- 价格区
- 文案区
- 家具主体

### 3. 不同图层类型最常进入哪种后续路径

例如：

- 产品图 -> 独立编辑
- 背景 -> 回贴验证
- 价格区 -> 局部替换

### 4. 哪类路径最容易通向“结果事件”

例如：

- 哪类动作后更容易导出
- 哪类动作后更容易入库
- 哪类动作后更容易复用

一旦能回答这 4 个问题，`Magic Layers` 就已经开始从 feature 变成 workflow 了。

## 十、和前两份文档的关系

这份文档不是独立存在的，它和前两份文档应该组成一条完整链路。

### 1. 和 `thought-completion-runtime.md` 的关系

`ChatPanel` 里解决的是：

- 用户还没想清楚时，怎么把想法写出来

`Magic Layers` 里解决的是：

- 用户已经把图导入并拆层后，怎么把下一步工作做出来

所以它们是：

- 上游表达补全
- 下游工作流补全

### 2. 和 `result-feedback-loop-analysis.md` 的关系

`Result Feedback Loop` 解决的是：

- 哪些结果被接受
- 哪些结果被导出、入库、复用

这些结果信号正是 `Magic Layers` 工作流能否变聪明的依据。

没有结果反馈，`Magic Layers` 只能学到“你做过什么”。

有了结果反馈，它才能学到：

- 哪条拆层路径更有效
- 哪类层更值得处理
- 哪类资产更值得沉淀

---

## 十一、第一阶段最适合的产品化目标

如果只做一个清晰、克制、能快速产生价值的第一阶段，我建议目标定义成：

> 让 `Magic Layers` 不再只是帮用户拆图，而是开始帮助用户判断拆完以后先做什么。

这个目标很重要，因为它不会把范围拉得过大，但又足够接近未来的 Runtime 方向。

### 第一阶段不要急着做：

- 复杂的多任务自动编排
- 强行业策略引擎
- 团队共享工作流模型
- 全自动资产价值判断

### 第一阶段先做：

- 记录入口
- 记录拆层后动作
- 记录结果信号
- 开始统计“哪类图层 -> 哪类动作 -> 哪类结果”

---

## 十二、如果未来做成，会演化成什么

理想状态下，`Magic Layers` 会慢慢具备下面这些能力：

### 1. 任务模式感知

系统知道当前是在做：

- 商品海报
- 餐饮促销
- 空间设计
- 详情页视觉变体

### 2. 图层价值感知

系统知道当前最重要的是：

- 主商品
- 价格区
- 文案区
- 主家具

### 3. 路径偏好感知

系统知道你在类似任务里更常：

- 先独立编辑
- 先回贴验证
- 先做局部风格同步

### 4. 资产沉淀感知

系统知道哪些拆层结果更适合：

- 保存为资产
- 进入模板
- 作为变体母版

这时 `Magic Layers` 就会真正像一个 workflow runtime 入口，而不是一个高级抠图功能。

---

## 十三、现阶段最适合的定义

当前阶段，可以这样定义这项工作：

> Workflow Completion for Magic Layers，不是让系统“多给几个建议”，而是让系统开始理解：当用户把一张图拆成可编辑资产之后，下一步最值得做什么。

这个定义很贴你们的产品方向，也能和 Runtime 主线保持一致。

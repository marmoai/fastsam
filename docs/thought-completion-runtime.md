# Thought Completion Runtime

本文档用于定义当前产品下一阶段要重点打磨的一个核心方向：

**让系统在用户还没有完整表达清楚之前，就能根据上下文、历史习惯、当前资产和当前任务，主动帮用户把想法续写出来，并在工作台中继续把下一步操作续做出来。**

这不是普通的 Prompt Autocomplete，也不是泛化的聊天补全。

对于 MarmoAid 这样的垂类视觉工作系统，它更接近于：

> 一个会持续理解用户任务、表达习惯、资产历史和操作路径的 Runtime 协作层。

---

## 一、为什么要做这个

当前系统已经具备：

- 图像语义拆层与 `Magic Layers`
- 图层编辑与回贴验证
- `Dispatcher -> CreativeMemoryLayer -> SemanticRecommender` 的行为记录与推荐骨架
- `ChatPanel` 中的初步补全机制

但这些能力目前还是分散的：

- Chat 里有补全
- 图层里有推荐
- Runtime 里有记忆

它们还没有被统一成一个“持续陪用户思考和续写工作流”的系统。

如果这一层成立，系统对用户的价值会从：

- “我帮你做一张图”

进化成：

- “我知道你想做什么、你通常怎么表达、你接下来大概率会做什么，并且我已经把下一步准备好了”

---

## 二、目标体验是什么

目标不是让系统“把句子补长”，而是让系统在两个层面同时变聪明：

### 1. Thought Completion

发生在 `ChatPanel` 中。

当用户输入还不完整、表达还模糊、甚至自己也还没完全想清楚时，系统就可以基于上下文给出高度贴近当前任务的续写建议。

例如：

- 用户输入：`我想做一款`
- 系统补全：`可以帮助用户记录日常饮食健康的手机应用程序`

对于 MarmoAid，这个补全应该更贴近视觉和设计任务，例如：

- `我想做一张` -> `适合新品促销的餐饮海报，保留主商品，强化价格区和视觉食欲感`
- `帮我把这个产品` -> `从当前背景中独立出来，做成可复用资产，再生成三种促销版式`
- `这张图我想改成` -> `更适合电商详情页的主视觉，保留主体结构，只调整材质、光影和背景氛围`

这里的重点不是补一个“正确句子”，而是补一个**符合当前任务上下文、并且用户大概率会接受的表达方向**。

### 2. Workflow Completion

发生在 `Magic Layers`、`Fusion Editor`、`Inspiration Capsule` 和工作台中。

当用户选中一个图层、刚完成一次拆层、或者刚做完一段局部编辑时，系统不仅要给风格建议，还要更进一步：

- 告诉用户下一步更适合做什么
- 提前浮出他常做的操作路径
- 在高频任务中把常用动作提前准备好

例如：

- 当前是商品图层：优先建议 `独立资产编辑 -> 保存资产 -> 批量变体`
- 当前是价格区：优先建议 `保持结构 -> 调整颜色/材质 -> 同步相关文案区`
- 当前是空间设计图：优先建议 `提取家具 -> 回贴到 clean plate -> 融合验证`

---

## 三、它和 Google AI Studio 的区别

Google AI Studio 的补全体验很强，但它的本质更偏：

- 通用表达续写
- 会话上下文理解
- 大模型对语言意图的通用补完

MarmoAid 不应该简单复刻这套体验，而应该做一套**更垂类、更贴资产和操作历史的补全机制**。

### 1. AI Studio 更偏通用语言助手

它擅长：

- 帮用户把模糊想法写完整
- 在会话里延续上下文
- 把一句普通需求整理得更清楚

### 2. MarmoAid 应该更偏“视觉工作 Runtime”

你们的补全不能只看文本，还必须看：

- 用户最近在处理什么项目
- 当前画布上有哪些资产和图层
- 用户最近常做哪些视觉任务
- 用户在类似图层上经常怎么改
- 哪些 prompt、参数、操作路径过去被接受过

所以差别是：

- AI Studio 是 **通用的 Thought Completion**
- MarmoAid 应该做 **带有资产历史、工作流历史和操作习惯的垂类 Thought Completion**

换句话说：

> AI Studio 更懂“语言怎么接着写”，MarmoAid 应该更懂“这个用户在这个视觉任务里下一步通常会怎么想、怎么说、怎么做”。

---

## 四、当前已经有的基础

现有系统并不是从零开始，这条路已经有明显基础：

### 1. Prompt 轨的基础

当前已有：

- `ImplicitMemoryEngine`
- `recordPromptStep()`
- `findMatch()`
- `registerImplicitSatisfaction()`

这说明系统已经能做：

- 记录一段 prompt chain
- 在主题切换时尝试收口
- 根据历史 `initialPrompt -> finalPrompt` 做一定程度的补全

但当前更偏：

- 历史命中
- 关键词前缀匹配
- 规则式补全

还没有真正进化成：

- 基于当前上下文动态生成“你现在正在想表达什么”

### 2. 图层轨的基础

当前已有：

- `Dispatcher`
- `CreativeMemoryLayer`
- `SemanticRecommender`
- `Fusion Editor / Inspiration Capsule`

这说明系统已经能做：

- 记录图层上的高质量行为
- 把行为映射成 `intent`
- 在图层级上下文里生成推荐
- 提供滑块配方、历史 prompt 和动态经验卡片

但当前更偏：

- 局部编辑建议
- 灵感卡片
- 参数和风格复刻

还没有完全进化成：

- 工作流级下一步推荐

---

## 五、当前距离目标还差什么

如果要达到你真正想要的体验，当前还差 5 个关键层次。

### 1. 从“字符串补全”升级到“意图补全”

现在更像：

- 输入前缀
- 命中历史规则
- 返回已有补全

目标应该是：

- 先判断用户这半句话属于什么任务意图
- 再结合当前上下文，生成最像他想表达的下一句

### 2. 从“仅看文本”升级到“融合工作台上下文”

补全时不仅要看输入框里的字，还要看：

- 当前 session 最近几轮对话
- 当前项目标题
- 当前画布上的主图和图层类型
- 当前是否处于 `Magic Layers` 工作流中
- 最近使用的资产和风格

### 3. 从“行为记忆”升级到“结果记忆”

如果没有结果层反馈，补全系统只能知道：

- 用户写过什么
- 用户改过什么

却不知道：

- 哪种补全被真正接受
- 哪种表达最终进入结果
- 哪种工作流建议带来了导出、保存、复用

所以 `Thought Completion Runtime` 必须和“结果级反馈闭环”一起成长。

### 4. 从“Chat 与图层两套脑子”升级到“同一个 Runtime”

真正理想的状态应该是：

- ChatPanel 知道用户当前在编辑哪些资产
- 图层编辑器知道用户最近在对话里表达了什么任务目标
- 灵感仓知道当前会话的主任务是什么

这样用户才会觉得系统一直在跟着他思考，而不是多个面板各说各话。

### 5. 从“推荐灵感”升级到“推荐下一步”

现在的推荐还偏：

- 风格卡片
- 参数复刻
- 历史意图复用

目标应该进一步走向：

- 当前最值得先处理哪一层
- 当前图更适合走哪条工作流
- 这个用户在类似任务里通常会先做什么

## 六、运行时应该利用哪些上下文

为了让补全真正变聪明，Runtime 至少要能接入以下上下文：

### A. 会话上下文

- 最近 5-10 轮对话
- 当前主任务关键词
- 当前项目标题
- 最近主题是否刚发生转移

### B. 画布上下文

- 当前选中对象
- 当前对象的语义类型
- 当前对象是否来自 `Magic Layers`
- 当前项目里主要有哪些对象类型
- 当前方案是否已有导出/回贴/拆层行为

### C. 用户历史上下文

- 最近接受过哪些补全
- 最近常用哪些 prompt 结构
- 最近常做哪些图层编辑操作
- 最近高频使用哪些资产

### D. 结果上下文

- 哪些补全被按了 `Tab`
- 哪些补全最终被发送
- 哪些推荐导致了导出
- 哪些推荐导致了入库、复用、保存

---

## 七、应该先怎么落地

不建议一步做到“像 Gemini 一样聪明”。更稳的路线是分三阶段推进。

### 第一阶段：把 ChatPanel 补全从“历史命中”升级到“上下文化补全”

先把以下上下文接进去：

- 当前 session 最近若干轮
- 当前项目标题
- 当前画布主要资产类型
- 当前用户最近被接受的补全记录
- 当前任务模式

目标不是生成很长的续写，而是先让补全变得**更贴当前项目与当前工作任务**。

### 第二阶段：把 `Tab` 接受与后续结果打通

补全不应该只记录“命中了”，还要记录：

- 用户是否按了 `Tab`
- 按了 `Tab` 后有没有继续大改
- 最终有没有发送
- 最终有没有触发编辑、导出、入库、复用

这是飞轮真正开始工作的地方。

### 第三阶段：让 ChatPanel 和灵感仓共享同一套意图状态

目标是做到：

- 当前会话里用户一直在做餐饮海报
- 当前画布上也全是餐饮商品和价格区
- 那么图层推荐与补全都应该开始偏餐饮任务

这样 Runtime 才会表现出“连续性”和“陪伴感”。

---

## 八、第一阶段建议采集的反馈信号

为了后续一条一条优化，先从少量高价值信号开始：

### ChatPanel 侧

- `completion_shown`
- `completion_tab_accepted`
- `completion_sent`
- `completion_edited_after_accept`
- `completion_abandoned`

### 工作台侧

- `recommendation_applied`
- `result_selected`
- `result_exported`
- `result_saved_to_asset_library`
- `result_reused`
- `result_reverted`

这些信号未来应该合并到同一个 Runtime 结果层，而不是继续各自分散。

## 九、如果这条路做成，用户会感受到什么

最终用户感受到的不应该是“这个补全挺好用”，而应该是：

### 1. 他说一半，系统已经懂了

输入不完整、表达模糊时，系统可以帮他把任务表述成更清楚、更可执行的语言。

### 2. 他点一个图层，系统已经准备好了下一步

不需要重新思考“我接下来该怎么办”，系统会主动浮出更贴当前任务的工作路径。

### 3. 系统越来越像他自己的工作搭档

不是“越来越像一个更强的大模型”，而是“越来越像一个懂他习惯、懂他资产、懂他任务节奏的工作伙伴”。

### 4. `Magic Layers` 不再只是一个 feature

而会逐渐变成：

- 一个任务入口
- 一个资产化入口
- 一个工作流起点

并且系统会随着用户高频使用它而越来越懂如何接住这条工作流。

---

## 十、当前最适合的定义

当前阶段，可以这样定义你们要做的东西：

> MarmoAid 的 Thought Completion Runtime，不是通用聊天补全，而是一个会结合用户任务、表达习惯、资产历史和操作路径，持续帮助用户“把想法写出来、把下一步做出来”的垂类视觉工作 Runtime。

这个定义既保留了你对 AI Studio 那种聪明感的追求，也明确了你们和通用工具的区别。
